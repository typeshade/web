이 페이지는 셰이더의 배정밀도 값 선언, 지원 연산, 에뮬레이션에 필요한 가드 텍스처 바인딩을 설명합니다.

GPU에는 64비트 부동소수점 타입이 없습니다. 이 패키지는 `f64`를 `f32` 두 개의 상위(hi)·하위(lo) 쌍으로 에뮬레이션합니다. 실제 값은 두 수의 합이지만, 계산 중에는 합치지 않고 쌍으로 유지합니다. 지수 범위는 f32와 같고 유효 비트는 약 48비트입니다. 유효 비트는 값의 자릿수를 유지하는 소수부 비트입니다. 1e8 근처의 월드 좌표에서 f32의 한 스텝은 이미 8 단위이지만, f64는 한 단위보다 훨씬 작은 차이를 구별합니다. `f64`는 다른 타입과 같은 방식으로 사용합니다. 백엔드 처리 전에 하향 변환 패스가 모든 f64를 `vec2<f32>`로 바꾸고 에뮬레이션 함수를 추가합니다. WGSL, GLSL, 기준값을 제공하는 CPU 오라클의 계산 결과는 모두 일치합니다.

48비트라는 수치는 GPU가 f32의 `+`, `-`, `*`를 최근접 값으로 반올림하고 중간값은 짝수 쪽을 선택한다고 가정합니다. 현재 출시된 GPU는 모두 이 방식으로 동작하지만, 두 사양 모두 이를 보장하지 않습니다. GLSL ES 3.00은 반올림 모드를 지정하지 않으며 비정규 수를 영으로 처리하는 것도 허용합니다. WGSL도 반올림 모드를 고정하지 않습니다. 따라서 이 수치는 하드웨어의 일반적인 구현에 의존합니다. 자세한 내용은 `docs/use-typeshade-surface.md`의 §39에 있습니다.

### f64 값 선언하기

유니폼 필드든, 매개변수든, 지역 변수든, `f32`를 쓰던 자리에 `f64`를 쓰면 됩니다.
연산자, 비교 연산, 내장 함수의 표기는 f32와 같으므로, f32로 쓴 본문을 f64로 바꾸면
대개 시그니처만 달라집니다.

```ts
"use typeshade";

class Uniforms {
  origin: f64; // one vec2<f32> slot: the host writes splitF64(value)
}

declare const u: uniform<Uniforms>;

export function k(x: f64, s: f32): f32 {
  return f32(sqrt((x + u.origin) * s));
}
```

모듈에 fp64를 쓴다고 따로 표시할 것은 없습니다. 하향 변환(lowering) 패스가 f64 타입을
스스로 찾아냅니다.

### 변환

f32와 f64를 함께 연산하면 f32는 값의 손실 없이 f64로 암묵적으로 확장됩니다. 따라서 f64인 `x`와 f32인 `dx`의 `x + dx`에는 별도 변환이 필요하지 않습니다. `f64(x)`는 확장을 명시하는 표기이며 산술 연산 전에 값을 f64로 만들어야 할 때 사용합니다. `f64`로 선언된 위치의 리터럴도 배정밀도 값을 유지합니다. 선언, 매개변수, 필드, 연산자의 반대편이 이에 해당하며 `f64(0.1)`도 같습니다. 좁히는 변환은 항상 명시해야 합니다. `f32(x)`는 hi와 lo를 더해 f32 하나를 반환하므로 f32에 담을 수 없는 정밀도는 사라집니다. f64에 대한 `%`와 정수 캐스트 `i32(x)`, `u32(x)`는 거부되므로 먼저 `f32`로 좁혀야 합니다.

```ts
"use typeshade";

export function g(a: f32, b: f64): f32 {
  const widened = f64(a); // exact
  const lit: f64 = 1e-9; // a literal in a declared f64 position keeps the double
  return f32(widened + lit + b); // the explicit narrow
}
```

소스에서 배정밀도 값을 두 워드로 분리하거나 다시 합칠 수는 없습니다. 스테이지 사이에 필요한 배정밀도 값은 각 스테이지에서 유니폼이나 스토리지 바인딩으로 읽거나, 스테이지 경계에서 `f32`로 좁혀야 합니다.

### f64가 지원하는 연산

사칙연산, 모든 비교 연산, `abs`, `cos`, `floor`, `fract`, `max`, `min`, `mix`, `round`, `sin`, `sqrt`는 f64 피연산자를 지원합니다. 나머지 연산은 호출 위치에서 거부되며, 진단은 지원 목록과 필요한 좁히기 변환을 안내합니다. 이 경우 `f32(x)`로 좁힌 뒤 해당 계산을 f32로 처리해야 합니다. `sin`과 `cos`는 다른 산술 연산보다 정확도가 낮습니다. 초월함수 자체의 상대 오차는 최선의 경우에도 약 2^-36이며, 인수가 커지면 인수 축소(range reduction)의 오차도 증가합니다.

```ts
"use typeshade";

// A triangle wave on a coordinate that has outgrown f32.
export function stripe(x: f64): f32 {
  const y = x * 0.5;
  const f = y - floor(y);
  return f32(min(f, 1. - f));
}
```

### 가드 텍스처

셰이더 컴파일러는 부동소수점 산술의 결합 순서를 바꾸기도 하는데, 그렇게 재결합하면 이
에뮬레이션이 기대는 작은 보정 항이 정확히 지워집니다. 그래서 생성된 헬퍼 함수마다 컴파일러가
미리 알 수 없는 값, 곧 텍스처에서 읽은 1을 보정 항 사이에 끼워 넣습니다. f64 산술이 이
헬퍼 가운데 하나라도 호출하는 모듈에는 `_fp64`라는 `texture_2d<f32>` 바인딩이 그룹 0의 첫
번째 빈 바인딩 자리에 자동으로 들어가며, `reflect()`에서는 보통의 2D 텍스처로 보입니다.
f64 값을 비교하거나, 넓히거나 좁히거나, 부호를 바꾸거나, 두 배, 절반 같은 이진 거듭제곱 배율로 스케일하기만 하는
모듈은 헬퍼를 하나도 호출하지 않으므로 바인딩을 받지 않습니다. 그러니 호스트는 모든
파이프라인에 `_fp64`를 바인딩하지 말고 `reflect()`를 읽어 판단합니다. 호스트는 텍셀 값이 정확히 1.0인
1×1 텍스처를 바인딩해야 합니다. 흰색 RGBA8이든 1.0을 담은 R32F든 상관없습니다. 이 값을
텍스처에 두는 이유가 있습니다. 일부 드라이버는 실제로 들어온 유니폼 값에 맞춰 파이프라인을
특수화하고 다시 최적화하는데, 그러면 보정 항이 또 사라집니다. 텍셀 값을 상수로 취급하는
컴파일러는 없습니다.

f64 산술을 하는 함수는 저마다 본문 맨 앞에서 텍셀을 한 번 읽고, 그 값을 헬퍼에 매개변수로
넘깁니다. 그래서 루프는 반복할 때마다 텍셀을 읽지 않고 시작하기 전에 한 번만 읽습니다.
GLSL에서는 이 텍스처를 `uniform highp sampler2D _fp64;`로 선언합니다. GLSL ES 3.00은 두
스테이지 모두에서 `sampler2D`의 기본 정밀도를 lowp로 정하고, 텍셀 읽기는 그 샘플러의
정밀도로 값을 돌려주기 때문입니다.

호스트는 바인딩 슬롯과 플랫폼별 하향 변환 방식을 정해야 합니다. 바인드 그룹 레이아웃이 고정되어 있으면 모듈의 바인딩에 `fp64Guard({ group, binding }).binding`을 추가해 슬롯을 고정합니다. Apple GPU는 기본 fast math가 부동소수점 기반 하향 변환을 무너뜨리므로 가드만으로는 충분하지 않습니다. 디바이스 정보를 `recommendFp64Flavor`에 전달하고 결과를 생성 옵션 `fp64Flavor`로 사용하면 이런 기기에 정수 기반 하향 변환을 선택합니다. 정수 기반 하향 변환에는 가드 바인딩이 필요하지 않습니다.

```ts
// m: the module of the first example on this page.
import { emitModule, fp64Guard, recommendFp64Flavor, type ModuleDecl } from 'typeshade'

const pinned: ModuleDecl = {
  ...m,
  bindings: [...m.bindings, fp64Guard({ group: 0, binding: 3 }).binding],
}

const flavor = recommendFp64Flavor({ userAgent: navigator.userAgent })
const wgsl = emitModule(pinned, { fp64Flavor: flavor })
```

생성된 셰이더에서는 에뮬레이션이 이름 공간 두 개를 차지합니다. `df64_`로 시작하는 함수
이름이나 `DF64Vec`, `DF64Mat`으로 시작하는 구조체 이름을 직접 쓰면 생성 시점에 `SD0043`
오류가 납니다.

### 패킹과 레이아웃

f64 유니폼 필드는 보통의 `vec2<f32>` 슬롯 하나를 차지하며, 크기는 8, 정렬은 8입니다.
호스트에서는 `splitF64(x)`로 값을 패킹합니다. 이 함수는 셰이더가 읽는 순서 그대로 `[hi, lo]`
쌍을 반환합니다. 버텍스 스테이지에서 프래그먼트 스테이지로 보간해 넘기는 값, 곧 varying은
f64일 수 없습니다. 삼각형 위에서 hi/lo 쌍을 보간하면 수치적으로 틀린 값이 나오기 때문입니다.
그래서 진입점의 `@location` 매개변수, IO 구조체 필드, 진입점의 반환값에 쓴 f64는 거부됩니다.
대신 f32 값을 보간하거나, 값을 유니폼으로 넘기고 f64 산술은 프래그먼트 스테이지에서 합니다.
스칼라 f64 버텍스 입력만은 예외입니다. 버퍼에서 읽는 값이고, 쌍이 슬롯 하나에 들어가기
때문입니다.

```ts
import { splitF64 } from 'typeshade'

const [hi, lo] = splitF64(-8_234_567.890123)
new Float32Array(uniformBuffer, 0, 2).set([hi, lo])
```

### 벡터

`vec2f64`, `vec3f64`, `vec4f64`는 벡터 타입이며 `vec2f64(x, y)` 같은 생성자로 값을 만듭니다. 성분 접근, 스위즐, f64·f32·숫자를 브로드캐스트하는 성분별 산술을 지원합니다. 스칼라 지원 목록에서 `sqrt`를 제외한 성분별 내장 함수와 `normalize`, f64 하나를 반환하는 `dot`, `length`, `distance`도 f32 버전과 같은 표기를 사용합니다. 레인은 읽기 전용입니다. `v.x = …`는 거부되므로 벡터 전체를 다시 만들어야 합니다. `vec3(v)`는 레인별로 값을 좁힙니다. 하향 변환 결과는 hi 평면과 lo 평면을 담는 구조체이며, 성분별 연산은 벡터 전체를 한 번에 처리합니다.

```ts
"use typeshade";

class P {
  center: vec2f64;
}

declare const p: uniform<P>;

export function d(x: f64, y: f64): f32 {
  const q = vec2f64(x, y) - p.center;
  return f32(dot(q, q)); // the subtraction and the dot both run in f64
}
```

벡터 유니폼 필드는 구조체와 같은 레이아웃을 차지합니다. std140에서 성분이 둘이면 16바이트,
셋이나 넷이면 32바이트입니다. 벡터 버텍스 속성은 슬롯 두 개가 필요하므로
거부됩니다.

### 비용

f64 연산 하나에는 여러 f32 연산이 필요하며, 곱셈이나 덧셈은 열 배 이상 걸리기도 합니다. 따라서 f64는 필요한 값에만 선택적으로 사용합니다. 넓은 범위의 좌표를 f64로 유지하고, 차이가 f32로 표현할 만큼 작아지면 좁혀 나머지 셰이더를 f32로 계산합니다.

```ts
"use typeshade";

// The subtraction needs the range; the shading after it does not.
export function shade(world: f64, camera: f64): f32 {
  return f32(world - camera) * 0.5 + 0.5;
}
```

f64 곱셈은 두 경우에 별도 코드 변경 없이 비용이 줄어듭니다. `x * x`는 제곱으로 처리되어 일반 곱셈보다 30%쯤 저렴합니다. 단, `x` 계산에는 스토리지 쓰기 호출 같은 부수 효과가 없어야 합니다. `2.0`, `0.5`, `-4.0` 같은 이진 거듭제곱 리터럴을 곱하거나 나누면 f32 워드 두 개의 배율만 바꿉니다. 오버플로와 언더플로가 없으면 결과는 정확합니다. f32 연산 두 번이 필요하며, `1.0`은 연산이 필요 없고 `-1.0`은 부호만 바꿉니다. 값이 커지는 배율(1보다 큰 경우)은 실행 시점에 계산하는 값에만 적용합니다. 상수에는 일반 곱셈을 유지합니다. WGSL은 셰이더 생성 시 상수를 평가하고 오버플로하는 상수를 거부하므로 이를 피하기 위한 처리입니다.

갤러리의 예제 중 하나인 `examples/fp64-lane-stripes.shade.ts`는 같은 수식을 두 타입으로 나란히
실행해서, f32 쪽은 평평한 필드로 뭉개지는 반면 f64 쪽은 줄무늬를 그대로 유지하는 모습을
보여줍니다.
