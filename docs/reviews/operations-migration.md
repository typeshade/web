# TypeShade operations workflow migration

Migrated the three TypeShade operational workflows from `apps/typeshade/.github/workflows/` to monorepo `.github/workflows/`: compiler pin proposals, example data publishing, and gallery setup. The workflows use root `pnpm install --frozen-lockfile` and the repository's pinned package manager; Bun 1.4.3 remains the runtime for TypeShade scripts. They initialize the compiler submodule at `apps/typeshade/vendor/shader-dsl`, while TypeShade-owned scripts run from `apps/typeshade` so their existing `vendor/`, `scripts/`, `dist/`, and `wrangler.gallery.jsonc` paths remain valid.

The compiler pin job retains full repository history, targets the app's submodule path for gitlink changes, and generates a proposal branch/PR rather than changing the compiler source. It asks the root CI workflow to validate the bot-created branch because GitHub suppresses the normal pull-request event for pushes made with `GITHUB_TOKEN`. The workflow is constrained to `main` and requires the repository variable `WEBSITE_OPERATIONS_ENABLED` to equal `true`, so it stays disabled by default during the repository cutover. Its write permissions are limited to contents, pull requests, and Actions dispatch. An open pin branch is rebased onto current `main` before the compiler update, preserving its review fixes; a real conflict fails for human resolution. It does not deploy the site.

`downstream-impact --repo typeshade.github.io` intentionally retains the compiler ecosystem's historic consumer key: compiler proposal metadata and `LINT.ThenChange(//typeshade.github.io/...)` records still name it. The script must run from `apps/typeshade` with `--submodule vendor/shader-dsl`, so its `src/...` target paths and git diff are relative to the TypeShade application, not the monorepo root. A read-only invocation against the current pin and an identical old/new SHA completed successfully and reported no findings.

The example publishing job remains scheduled, manually runnable, and callable with the existing `compiler-updated` repository dispatch. It requires the same opt-in repository variable, uses the protected `typeshade-production` environment for Cloudflare credentials, and exposes the token only to the credential check and upload steps. The manual compiler ref is validated as a legal branch name or full SHA and rejects option-like values before fetch. It reads examples at the requested compiler ref and applies localized site copy at the pinned compiler. The gallery setup workflow is manual-only, requires the same opt-in variable, and restricts both jobs to `main`; both it and publishing share the `deploy-typeshade` concurrency group used by TypeShade deployment. Its Cloudflare token is scoped to the still-upload and Access-configuration steps only. Stills are stored as an artifact under `apps/typeshade/gallery-stills`, and Access configuration reads the reviewer address from the event, masks it, and runs inside the protected `typeshade-production` environment.

The integration also updates public GitHub source/edit links and the link-checker's own-file
mapping to `typeshade/web/apps/typeshade`. The issue form now routes site reports to
`typeshade/web`; its GitHub App installation access is a documented cutover prerequisite.
The compiler consumer key and historical source repository remain unchanged intentionally.

Validation: actionlint passed on all three TypeShade workflows; PyYAML parsed them and `bash -n` passed for every embedded `run` script. A synthetic compiler git history changed a `LINT.IfChange` block targeting `//typeshade.github.io/src/copy.ts`; running `downstream-impact` from the synthetic `apps/typeshade` root correctly reported the untouched `src/copy.ts`, verifying app-relative path mapping with a meaningful ThenChange case. The current-pin no-diff invocation also passed. No workflow was dispatched, no external service was called, and no commit or push was made.

## TypeCV lab operations

Added monorepo workflows `typecv-lab-records.yml` and `typecv-lab-samples.yml` from TypeCV's previous `lab-records.yml` and `lab-samples.yml`. Both are manual-only, main-only, require `WEBSITE_OPERATIONS_ENABLED == 'true'`, use the protected `typecv-production` environment, share `deploy-typecv` concurrency with the TypeCV deployment, and declare only `contents: read`. They use the root frozen pnpm install where Wrangler and ffmpeg-backed sample publishing need dependencies, while Node scripts run from `apps/typecv` so their config, manifest, and script-relative paths resolve as intended.

The record exporter accepts only a bounded integer limit (1–100) and the three documented print modes, passed through environment variables rather than interpolated into shell code. An optional comma-separated record-id input preserves targeted exports from the latest upstream. Hardware-check records are compared with the checked-in CPU baseline, and their tables are written to the workflow summary; failed comparisons do not discard the exported evidence. Its Cloudflare token is scoped to the export step. The exporter retains the existing `lab-records` artifact name and 14-day retention. The JSON contains consented diagnostic telemetry such as user agent, adapter, fixture/camera values, timings, and errors; by default failed records are printed in the workflow log, and the `all` mode prints every record. It does not fetch private run-result files, which may contain visitors' photos or video. This workflow preserves that developer-diagnostics behavior; public artifact/log visibility is a remaining operational policy consideration.

The sample publisher only processes ids in the checked-in manifest, verifies source-video hashes unless the script's explicit `--update` mode is used (not exposed by the workflow), and uploads to the configured R2 bucket. It has no deletion path and no scheduled trigger. Production deployment remains a separate manual workflow and does not delete sample or record data.

Validation: actionlint passed on both TypeCV workflows; PyYAML parsed them and `bash -n` passed for each embedded shell block. No workflow was dispatched, no Cloudflare API was called, and no sample/artifact was uploaded or removed.
