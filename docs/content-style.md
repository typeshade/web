# Website content

English is the source for TypeShade, TypeNN, TypeCV and shared UI copy. Write and review the
English first, then translate it into Korean. A translation preserves the same claims,
qualifications, examples, calls to action and section order. Adjust grammar and word order for
Korean; do not add a separate slogan, explanation or product promise.

## References

The owner's references are the official [Blend2D](https://blend2d.com/),
[React](https://react.dev/), [Vue](https://vuejs.org/),
[MapLibre GL JS](https://maplibre.org/maplibre-gl-js/docs/) and
[Mapbox GL JS](https://docs.mapbox.com/mapbox-gl-js/guides/) sites.
The [React Korean site](https://ko.react.dev/) and
[Vue Korean guide](https://ko.vuejs.org/guide/introduction) illustrate translated documentation.
Use their approach to developer communication, with original wording specific to our products.

- Introduce the product category, what developers can build and the supported environment.
- Explain a feature with an operation, example or API a reader can use.
- Use task headings where appropriate: writing a shader, training a model, installing a package.
  Product names and conventional labels work for navigation and reference pages.
- Address the reader directly in tutorials and calls to action. Questions and imperative
  headings are useful when they fit the subject; they are not automatically writing errors.
- Keep prose connected. Do not turn each explanation into a list of short fragments or paired
  slogans. Do not repeat a heading in the first sentence without adding information.
- Describe supported behavior and keep limitations next to the feature they qualify.
  Distinguish current functionality, experiments and roadmap items. Keep measured results
  tied to their conditions and source.
- Use established technical names. Explain unfamiliar terms in context instead of inventing
  a label or using internal implementation vocabulary as a product benefit.

## Translation and review

Review all published surfaces: headings, paragraphs, navigation, buttons, form help, empty
states, errors, accessibility labels, metadata, examples, generated reference and imported
project documentation. Text inherited from a source package is still part of the review.

Review English for usefulness and technical accuracy before translation. Review Korean against
that English for meaning and tone, then read it for grammar and idiom. Keep API identifiers,
code, numerical results, links and support conditions intact. Retain stable section anchors
when changing headings.

Automated checks help find missing translations, broken links and formatting errors. They do
not decide whether prose sounds natural. Do not rewrite good prose to satisfy a sentence-count
rule or a blanket ban on ordinary words. Record the reviewed scope and unresolved source issues
in the content review record.
